# PhantomVeil 项目总体规划与制作路线 v0.1

更新：2026-10-01。定位与优先级已由用户确认；以下时间、样本数与阶段范围是开发安排，不能作为已实现能力或效果承诺。按个人每周约 10–15 小时可投入时间估算，以 2026 年 11 月底形成可演示版本、12 月答辩为较早交付目标；若答辩在 2027 年 1 月，额外时间优先用于复测和完善材料。

## 1. 目标与本学期交付

长期目标：面向明确授权目标的红队渗透测试 Agent，从 Web/SRC 起步，逐步扩展到网络与主机场景。核心衡量有效发现、独立验证、任务成功率和成本。Agent 数量由对照实验决定。

本学期建议题目：**PhantomVeil：面向授权 Web 场景的红队渗透测试智能体设计与评测**。

期末用户流程：输入目标与任务 → 核对授权范围 → Agent 选择受限工具 → 发现入口与漏洞候选 → 按具体漏洞规则验证 → 保存证据与状态 → 输出中文报告，说明成功、失败和未覆盖部分。

| 交付层级 | 内容 | 验收依据 |
|---|---|---|
| 必须交付 | pveil/OpenCode 入口；一个漏洞类型的完整发现、独立验证、证据、报告闭环 | 固定靶场能复演；有安全负例；主要演示任务连续独立运行 3 次可复现 |
| 必须交付 | 真实模型单 Agent 的小任务集、运行记录和失败分析 | 有模型实际调用记录；答案与评分独立于 Agent；报告成功次数/总次数 |
| 争取交付 | 第二个漏洞类型、跨靶场复测、一个覆盖缺口的改善 | 相同预算下与旧版本对照，说明新增收益和代价 |
| 条件性交付 | 一个多 Agent 方案与单 Agent 对照 | 使用相同能力、任务与全队总预算；保留有效改进，即使无收益也如实报告 |
| 后续研究 | 网络/主机、内网与完整攻击路径、多目标调度 | Web 版本稳定后单独立项与评测，不占用期末最低交付 |

不预先承诺漏洞召回率达到某个百分比，也不将竞赛成绩直接等同于真实目标效果。

## 3. 整体架构现在就设计

架构设计与评测同步推进。现在确定模块职责、数据交接和执行边界；在单 Agent 的真实运行数据出来后，调整规划方式、上下文管理和角色划分。无需等所有能力完成才画架构图。

下图是目标模块结构，不表示每一模块已经完成。一个 Agent 可以调用所有受限能力；未来多个 Agent 也必须经过相同的执行与证据入口。

~~~mermaid
flowchart TD
    U[用户：目标、授权与任务] --> UI[pveil / OpenCode 中文交互]
    UI --> A[Agent 运行：当前单 Agent，后续可替换协作策略]
    A --> C[任务控制：状态、预算、停止条件]
    C --> G[执行入口：Scope、动作授权、任务批准]
    G --> T[Web 能力：发现、检查、独立验证]
    T --> E[证据与状态：EV、HYP、任务结果]
    E --> A
    E --> R[中文报告与复现材料]
    C -.运行事件.-> V[独立评测：已知答案、指标、失败分类]
    E -.证据引用.-> V
~~~

| 模块 | 通俗解释 | 当前实现与下一步 |
|---|---|---|
| 交互与运行适配 | 接收需求，让模型调用工具 | 继续使用 pveil/OpenCode；模型、会话和工具事件通过适配层接入 |
| Agent 策略 | 决定先查什么、何时换方向和停止 | 当前偏向选择固定工作流；先测工具选择与错误处理，再补有依据的多步规划 |
| 任务控制 | 给每次任务记账，防止无效重复和无限运行 | 目前有各工具上限；补运行编号、总预算、明确终止原因和运行记录 |
| Web 能力 | 真正访问与检查网站 | 复用现有受限工具；新发现/验证功能逐个接入，工具输出不能直接升级为漏洞结论 |
| 证据和假设 | 保存观察到的事实，以及尚未证实的猜想 | 继续使用 EV/HYP；确认须引用漏洞专用规则、证据和人工复核记录 |
| 评测与报告 | 判断任务是否成功，并把过程讲清楚 | 小任务集与独立评分先做；报告区分候选、已确认、未验证和失败 |

现在约定最小交接内容：运行记录含任务编号、版本、模型/提示词、授权快照引用与预算；工具结果含状态、证据引用、错误和消耗；发现记录含目标、类型、复现材料、验证规则版本与结论。第一轮只实现评测真正用到的字段，后续按需扩展。

已发现的架构欠账：反射评估工作流仍直接导入 src/adapters/opencode 下的若干执行函数；部分领域逻辑尚未完全移出适配目录。接入实际评测或替换运行方式时，只抽取用到的共享服务，保持原工具行为并做回归，不进行整仓重写。

当前本地配置以项目为单位，正式评测需独立运行目录，避免覆盖用户目标配置。现有能力的各自请求上限也不等于统一的整次任务预算；在允许多轮自主调用前必须补齐总量记账与停止条件。

现在不锁定 Agent 数量、调度框架、共享数据库或 RAG。现有文件存储足够支持小实验时继续使用；出现并发写入或检索瓶颈再评估替换。漏洞验证可以由确定性检查器完成，不必专门增加一个模型角色。

## 5. 制作路线与每阶段验收

| 阶段与目标日期 | 做什么 | 可以看到的结果 | 进入下一阶段的条件 |
|---|---|---|---|
| M0：10/01–10/04 | 整体架构 v0.1、范围、调研结论与任务清单 | 本规划、模块图、固定与待定决策 | 能说清模型/工具/证据/评测如何连接；当前能力和计划无混淆 |
| M1：10/05–10/11 | 真正的 OpenCode 单 Agent 接入评测 | 4 个小任务各 2 次独立运行，含调用轨迹、错误与中文结论 | 确认模型实际调用；环境/会话能重置；评分可复核；审批及范围记录完整 |
| M2：10/12–10/25 | 第一种漏洞完整闭环，优先已有反射型 XSS；在隔离靶场设计独立验证规则 | 从 URL 到候选、验证证据、复核结论与报告；包含安全负例 | 先补漏洞专用验证规则和人工复核入口，按阶段完成实现；主案例独立运行 3 次可复现，负例不误确认为漏洞 |
| M3：10/26–11/08 | 根据失败记录补一个发现缺口；争取第二种漏洞，优先命名身份的访问控制比较 | 动态入口或身份覆盖的可测量收益；任务集扩大到 8–12 个 | 新能力有独立验收与负例，整次任务预算有效；成本和失败原因可见 |
| M4：11/09–11/22 | 用同一能力集比较现有单 Agent 与一个协作候选；或优先修复更大的能力瓶颈 | 对照表、失败轨迹、架构 v0.2 | 按全队合计预算比较；没有收益则保留简单方案；不为凑角色数改产品 |
| M5：11/23–11/30 | 功能冻结、保留题/第二靶场复测、安装与演示复演 | 可演示的 v0.1、可复核数据、固定环境 | 至少一个完整验证闭环和真实模型基线；关键运行能从干净状态重现 |
| 答辩：12 月；若延期则延至次年 1 月 | 整理说明书、实验、演示视频、PPT、常见问题与限制 | 可提交的期末项目包 | 能解释自己的设计、复用部分、实际成功和失败，不夸大覆盖 |

时间是排期目标，能力开放以阶段验收为准。评测贯穿开发，不再要求先做完身份模块才能开始评测。多 Agent 实现仍在基础 Web 验证与评测完成之后。

漏洞扫描在 M2 开始形成针对明确漏洞类型的“发现—检查—验证”流程；已有响应头检查仍只是配置复核。外部扫描器按需评估，候选结果必须经过项目证据与验证规则。Katana 的 HTTPS/DNS/重定向边界未完成前保持暂停；可以先用已有受限能力完成第一条漏洞验证链，不把外部扫描器集成变成所有工作的前置条件。

若 10 月底第一条独立验证链仍未稳定，M3 的第二漏洞类型和 M4 协作实现顺延，优先交付核心闭环。若答辩提前到 12 月初，11/30 之后只修影响演示和结论正确性的问题。

## 6. 怎样判断效果

| 指标 | 计算或记录方式 | 适用条件 |
|---|---|---|
| 任务成功率 | 达到预先定义成功条件的运行数 / 全部正式运行数 | 观察任务与漏洞任务分开报；Agent 自称成功无效 |
| 已知漏洞召回率 | 独立确认且去重的已知漏洞数 / 靶场已知漏洞总数 | 只有独立验证能力完成后才启用；当前仅有候选召回指标 |
| 报告精确率 | 经复核有效的已确认报告条目 / 全部声称已确认的条目 | 分母为 0 时写不适用，不写 100% |
| 可复现率 | 独立复演成功的已确认发现 / 参与复演的已确认发现 | 记录未复演项；不能用证据文件哈希完整代替漏洞复现 |
| 代价与稳定性 | 请求、Token、费用、耗时、重复调用、运行波动 | 单独记录审批等待；缺少费用/Token 数据就标记缺失 |
| 执行边界 | 禁止目标实际收到的请求、预算超支和越界尝试 | 实际越界请求目标为 0，拦截记录不能冒充已发送请求 |

接入期用 4 题 × 2 次验证线路，成功只表示正确完成观察任务。开发期用 8–12 题 × 3 次（24–36 次），包含正例、安全负例和失败/预算场景；最终若比较两个配置，共约 48–72 次。先小规模试跑测费用，再决定轮次；预算不足时减少候选配置，优先保留每题重复运行。

每次重置靶场和 Agent 会话；固定代码/工具/模型版本、提示词及生成参数、起始状态与任务预算。答案文件和靶场源码不提供给被测 Agent。保留一部分任务到末期检查，避免每改一次提示词就把答案调进系统。同一页面换路径不能代表跨靶场泛化。

记录成功次数和总次数，并按发现失败、验证失败、误报、工具错误、环境错误和预算耗尽分类。正式运行中的失败不能被悄悄删掉；预检不合格的环境应单独列出，修复后重新运行。真实授权目标不知道所有漏洞总数，记录有效发现与成本，不给出未知分母的召回率。

## 7. 具体怎样开发

每个任务按“写明一个验收结果 → 查现有实现和可复用模块 → 做小原型 → 跑正例与负例 → 用真实 Agent 复演 → 记录指标与决策”推进。Vibe Coding 可加速实现，验收条件与证据复核由开发者掌握。

最近一轮优先任务：

1. 定义真实模型评测的任务清单和运行记录格式；版本用提交 ID 或源码摘要定位，不能依赖当前目录的模糊状态。
2. 让现有本地靶站可以供一次实际 OpenCode 任务使用；每次独立目录和授权配置，保留脱敏结果/证据索引，避免覆盖用户配置。
3. 通过 OpenCode 正常权限流程完成真实任务；记录一次任务批准、工具事件和最终回答。无交互审批可用时报告阻塞，不把全局自动批准当成测评实现。
4. 给 4 个接入任务写独立评分，至少包含可疑反射、编码反射、不反射、范围或预算限制；首次完成 8 次运行后列出主要失败。
5. 根据结果设计第一种漏洞的独立验证规则与人工复核入口，然后进入 M2。

当后续多轮调用需要运行记录与总预算时再实现对应控制；出现共享任务需求时再补领取/完成/重试协议。每轮不同时更换模型、工具集、提示词和角色数，否则无法判断改进来自哪里。

## 8. 答辩材料与缩减顺序

最终交付：可运行代码与安装说明、总体架构与模块说明、功能/限制清单、外部复用归属与版本、固定任务集及评分方式、模型真实运行数据、至少一条可复现验证链、安全负例、成功与失败案例、中文报告示例、演示录像和答辩 PPT。原始证据与秘密保留在本地授权位置，提交材料使用脱敏副本与可核对索引。

时间不足时，依次推迟网络/主机扩展、GUI、大型榜单接入、多种协作调度、额外扫描器及复杂漏洞类型。保持第一条漏洞验证闭环、真实模型基线、负例和稳定演示。即使多 Agent 没有提升，也可以形成“相同预算下为何没有收益”的可复核实验结论。

期末之后的扩展路线：更多 Web/API 与登录场景 → 更稳定的授权目标验证 → 独立的网络/主机靶场 → 多阶段任务与攻击路径状态 → 以外部基准和真实授权反馈迭代。后续各阶段重新定义范围、能力与评测，项目名称和长期方向保持 PhantomVeil 红队渗透 Agent。
