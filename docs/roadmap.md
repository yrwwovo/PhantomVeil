# PhantomVeil 制作路线

更新：2026-10-01。完整目标、模块架构、评测定义、复用来源和答辩交付见 [项目总体规划 v0.1](project-plan.md)。当前实现与限制见 [TASK.md](../TASK.md)。

长期目标是面向明确授权目标的红队渗透测试 Agent，从 Web/SRC 起步。优先提高可复现发现、验证和任务成功率；Agent 数量由实验决定。整体架构现在设计，评测贯穿开发。

| 阶段 | 目标时间 | 交付与验收 |
|---|---|---|
| M0：模块架构与制作规划 | 10/01–10/04 | 架构 v0.1、模块职责、待定决策和任务清单；本规划已建立，后续只补具体复用审查 |
| M1：真实单 Agent 接入评测 | 10/05–10/11 | 4 个观察/边界任务各 2 次实际模型运行；独立配置与会话、工具事件、证据索引和可复核评分 |
| M2：第一类漏洞验证闭环 | 10/12–10/25 | 优先反射型 XSS；先建立漏洞专用验证规则与人工复核入口，在隔离靶场完成正例、负例和重复复演 |
| M3：覆盖与第二类能力 | 10/26–11/08 | 按失败记录修复一个发现缺口；争取命名身份/访问控制比较；任务集扩大至 8–12 题 |
| M4：架构对照 | 11/09–11/22 | 单 Agent 与一个协作方案使用相同模型、工具、任务及全队总预算比较；收益不足时保持简单实现 |
| M5：功能冻结与复演 | 11/23–11/30 | 保留题与第二靶场检查、安装复现、报告和演示；最低交付为一类验证闭环与真实模型基线 |
| 答辩准备 | 12 月；必要时至 2027 年 1 月 | 说明书、实验数据、复用说明、视频和 PPT；增加复测时间，不预先扩张功能 |
| 长期研究 | 期末核心交付之后 | 更多 Web/API、网络/主机场景与多阶段任务，逐项重新定义范围和验收 |

日期按个人每周约 10–15 小时估算，具体进展按验收判断，不因日期到达自动开放能力。若 M2 未稳定，第二漏洞类型与协作实现顺延。

## 已有基础

pveil/OpenCode 受限工具接入、Scope 与动作授权、受限 GET、静态同源爬取、EV/HYP、中文报告和反射/编码候选评估已经存在。详细完成记录保留在 TASK.md 和各功能文档，避免在此重复维护实时状态。

[本地工作流基线](../benchmarks/web-baseline/README.md) 已建立；它没有调用模型，也没有确认漏洞。实际 Agent 运行与独立漏洞验证是下一阶段的明确缺口。

## 依赖关系

- M1 可以直接复用已有工具，不以身份模块、外部扫描器或多 Agent 为前置条件。
- M2 的确认功能须先有漏洞专用验证规则、证据和人工复核入口。现有 suspected 结果保持原含义。
- 新工具接入须完成具体复用决策与边界验证；Katana 当前仍暂停。继续出站门禁研究是候选工具路线，不阻塞现有能力评测。
- M4 之前必须有稳定的 Web 验证链和单 Agent 结果；共享任务/状态和调度按实验需要实现。
- 协作比较要固定总预算，多个 Agent 不能各自获得一整份单 Agent 预算后直接声称架构更好。
- 真实授权目标漏洞总数未知，记录去重有效发现、误报与代价，不计算未知分母的发现率。

## 架构评审时间

现在完成 v0.1 模块与接口设计；M1 后根据真实调用记录检查适配与预算边界；M2/M3 后根据主要失败选择协作实验；M4 后形成期末采用的 v0.2。评审关注可测量的问题，不以引入更多框架或角色为完成标志。
