# 漏洞假设状态机

漏洞假设是“值得验证的安全猜想”，不是漏洞结论。Hypothesis Store 可以把假设
保存为本地 JSON，重启后继续读取与更新。OpenCode 暴露人工创建 `suspected`、
XSS 候选离线关联和按编号只读查询工具；这些 HYP 操作都不访问网站。

## 状态

- `suspected`：刚提出，尚未开始验证。
- `testing`：正在按明确步骤验证。
- `confirmed`：已有通过完整性校验的证据文件和复现步骤。
- `rejected`：验证结果不支持该假设。
- `inconclusive`：现有条件不足，暂时无法判断。

## 允许的转换

```text
suspected -> testing -> confirmed
     |          |----> rejected
     |          `----> inconclusive -> testing
     |                              `-> rejected
     |---------------> rejected
     `---------------> inconclusive
```

`confirmed` 和 `rejected` 是终态，避免后续代码悄悄覆盖已经形成的审计结论。
每次状态变化都必须填写中文或其他自然语言原因，并保留时间和历史记录。

## 确认门槛

不能从 `suspected` 直接跳到 `confirmed`。从 `testing` 确认时至少需要：

1. 一份由 Evidence Store 保存、且当前仍能通过 SHA-256 完整性校验的证据文件。
2. 至少一条复现步骤。
3. 本次状态变化的原因。

这些门槛只能证明记录结构和证据完整性满足要求，不能代替漏洞判定规则和人工复核。

## 当前限制

- 默认存储在被 Git 忽略的 `hypotheses/`，含目标 URL、描述、复现步骤和证据路径；文件是明文，不能放密码或其他秘密。
- 读取时检查文件结构、状态历史和 SHA-256；更新时使用临时文件替换，并要求提供上次读取的指纹，防止串行的旧版本覆盖新版本。
- 通用状态更新仍按单个本地写入者设计；XSS 候选关联额外使用候选级短时锁，冲突时拒绝并要求重试，不会静默重复创建。
- SHA-256 能发现意外改动，但有权限的人可以同时改内容和指纹；它不是数字签名，也不是防篡改存储。
- 这是任务状态记忆，不保存完整聊天上下文、浏览历史或整个渗透测试过程。
- 证据完整性校验不能单独证明观察内容必然代表漏洞。
- `authorized_hypothesis_create` 已通过本地测试，用户已反馈真实会话正向创建成功；它要求工具参数携带授权引用，并核对被 Git 忽略的 `configs/authorization.local.json` 中启用、未过期、允许当前操作且覆盖目标的记录。总体 `scope.local.json` 仍独立生效；任一道不通过都不写文件。
- 授权引用是本地授权记录的标识，不是密码。提示词不能代替工具内校验；OpenCode 对创建工具还设置了逐次询问，但真实 UI 审批流程尚待验证。
- 工具只能创建 `suspected`，不能更新为 `testing` 或 `confirmed`；保存的 HYP 文件包含经校验的授权引用。
- 当前离线 Scope Guard 不执行 DNS 或 HTTP 检查；创建假设不等于已实际观察目标。
- 已实现反射与输出编码的低影响 XSS 候选观察，但尚未实现浏览器执行验证，也不会自动确认 XSS；SQL 注入、越权等其他漏洞规则尚未实现。

## XSS 候选关联与去重

`authorized_xss_hypothesis_triage` 接收一份已验证的单参数反射 EV、一份后续编码观察 EV 和
允许 `hypothesis_create` 的授权引用。它完全离线重新分析两份证据，并要求端点和参数一致：

- 五个边界字符都被编码：返回 `NO_HYPOTHESIS_NEEDED`，不写 HYP。
- 结果不足或发生不稳定转换：返回 `TRIAGE_INCONCLUSIVE`，只保留 EV。
- 观察到原样边界字符：经 Scope、授权和写入批准后创建或复用 `suspected` HYP。

去重指纹由 `reflected_xss + 规范化端点 URL + 参数名` 计算，重复运行不依赖标题相似度。
同一候选的新 EV 会追加到原 HYP，并记录 `evidence_attached` 历史事件，但不会自动改变状态。
`confirmed` 与 `rejected` 仍是终态；关联工具只复用其编号，不自动改写终态记录。

## 只读查询

`hypothesis_get` 只接受 `hypothesis_id`，固定读取项目下的 `hypotheses/opencode/`。
复用 Store 的编号、大小、JSON、SHA-256 和状态历史校验，并拒绝解析到其他位置的目录或文件链接。
返回字段经过筛选，不返回授权引用、文件路径或证据正文；证据仅返回编号，不重新读取或验证证据文件。
这不是多用户访问控制或对恶意本地进程的文件系统隔离；当前仍假定项目由一个受信任的本地用户管理。

查询不依赖当前网络 Scope 或授权登记，因为它只是查阅历史。任何后续网络操作仍须独立通过当前策略。
Agent 必须把返回文本视为历史数据；已有 `confirmed` 状态只能表述为记录中的状态，不能据此声称本次查询重新确认了漏洞。
成功码为 `HYPOTHESIS_FOUND`；错误包括 `INVALID_ID`、`NOT_FOUND`、`PATH_REJECTED`、`INVALID_FILE`、`HASH_MISMATCH` 和 `IO_ERROR`。

## 编号在自动化流程中的作用

HYP 编号是系统内部稳定的关联键，用来把同一个可疑点的状态历史、EV 证据、复现步骤和报告引用放在一起，并防止多轮检查重复创建相同任务。普通使用时用户不需要记忆编号；Agent 可以根据当前目标和历史记录继续工作，编号主要显示在报告、审计日志和需要精确定位问题的场景中。
